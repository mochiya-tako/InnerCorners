# InnerCorners GitHub公開・未実装ホットコーナー機能拡張計画

- 策定日：2026-11-13
- 基準版：InnerCorners v0.10.3 (build 46)
- 対象：GitHubでのソース公開、および必要に応じた署名済みバイナリ配布
- 対象外：Mac App Storeへの提出・審査対応
- 本文書の目的：短時間の作業枠でも、安全に中断・再開できる実装順序と完了条件を固定する

## 1. 現在地

### 実装済みの標準ホットコーナーアクション

- Mission Control
- アプリケーションウインドウ（App Exposé）
- デスクトップを表示
- アプリ（macOS 26以降のApps.app／旧OSのLaunchpad.app）

これらは特定の角へ固定されていない。各画面・各角についてmacOS側の現在の割当を読み、対応するアクションを実行する。

### 未実装の候補

- スクリーンセーバーを開始
- スクリーンセーバーを無効化
- ディスプレイをスリープ
- 通知センター
- 画面をロック
- クイックメモ
- Command／Shift／Option／Controlを条件にした修飾キー付きホットコーナー

macOSのバージョンによって選択肢、設定値、起動方法が変わる可能性がある。上記一覧とDock設定値は、実装前に各対象OSで再確認する。

### 現行版で保留している潜在リスク

- 1000 Hz級マウスを壁へ長時間押し当てた際の連続`CGWarpMouseCursorPosition`負荷
- イベントタップコールバック内の`MainActor.assumeIsolated`
- OSの復帰通知を意図的に欠落させた場合の前面化フェイルセーフの実機再現
- Sidecar、ミラーリング、縦一列・T字配置の実機試験

いずれも現時点で再現した不具合ではない。特にワープの間引きは高速移動時の貫通を再発させ得るため、実測なしに変更しない。

## 2. 開発原則

1. 「内部コーナーを外周ホットコーナーと同様に通過不能にする」という主機能を最優先する。
2. 新しいアクションの失敗が、壁、Option緊急通過、`⌃⌥⌘Q`、スリープ安全機構へ影響しない構造にする。
3. Appleの公開APIを第一候補とする。
4. 非公開シンボル、非公開通知、SIP回避、恒久的なシステム設定変更は採用しない。
5. 公開APIがない機能は、標準ショートカット、ユーザー指定ショートカット、未対応の順で判断する。
6. OS設定値が未知の場合は推測で実行せず、「未対応」と診断表示する。
7. コード変更ごとに、壁の高速衝突、厳密角、再衝突キャンセル、スリープ復帰の回帰を確認する。
8. 実機で確認していない項目を「動作確認済み」と記載しない。
9. 一つの作業枠では原則として一つの課題IDだけを完了させる。
10. バージョン番号、README、成果物名、診断表示を同時に更新する。

## 3. 公開経路

### A. ソースのみGitHub公開

Apple Developer Programへの加入やDeveloper ID証明書は不要。利用者が自分でビルドする形になる。

必要事項：

- ライセンスの選択
- 公開前の秘密情報・個人情報・不要ファイル検査
- 自己完結したソース一式
- ビルド手順、必要権限、安全な終了方法の説明
- 既知の制限と検証済みOS・画面構成の明記

### B. GitHub Releasesでアプリも配布

一般利用者向けにはDeveloper ID署名とApple公証を原則とする。現在のアドホック署名版をそのまま公開版とはしない。

追加で必要なもの：

- Apple Developer Program
- Developer ID Application証明書
- Hardened Runtime
- 安全な公証用認証情報の管理
- `notarytool`による公証と`stapler`によるチケット添付
- Gatekeeper検証
- クリーンな別ユーザーまたは別Macでの初回起動・権限付与試験

参考：

- Apple「Use hot corners on Mac」：<https://support.apple.com/guide/mac-help/mchlp3000/mac>
- Apple「Notarizing macOS software before distribution」：<https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution>
- Apple「Developer ID certificates」：<https://developer.apple.com/help/account/certificates/create-developer-id-certificates/>

## Phase 1：仕様調査と実行基盤

### P1-01 OS別アクション表の作成

- 所要：2～4時間
- 対象：macOS 14、15、26、27
- 作業：各標準アクションのDock設定値、名称、修飾キービット、公開された実行手段を表にする。
- 完了条件：各項目が「公開API」「標準ショートカット」「ユーザー指定が必要」「対応不能」のいずれかに分類され、根拠が記録される。
- 禁止：ブログ等の単一情報だけを根拠に設定値を確定しない。
- 現状：macOS 27.0.1の全選択肢、現在割当、実行候補まで記録済み。未割当raw値の直接照合とmacOS 14／15／26の確認は未完了。

### P1-02 ActionExecutorの責務整理

- 所要：2～4時間
- 依存：P1-01
- 作業：アクション要求、非同期完了、失敗理由、必要権限を統一的に表現する。
- 完了条件：`performed`、`requested`、`permissionRequired`、`unsupported`、`failed`を診断上区別できる。
- 回帰条件：既存4機能の割当変更と再衝突キャンセルが維持される。
- 現状：実装・コンパイル確認済み。Dock値を`SystemHotCornerAction`へ分離し、既知の未実装機能、未知値、実行失敗、意図的スキップを診断上区別。12値の独立検証に合格。v0.11.0 beta 2では壁衝突と独自矩形領域を`trigger`で区別し、数値ディスプレイID、角、解決後のアクション、結果コードを統合ログへ記録する。表示名、前面アプリ名、詳細理由は統合ログへ出さない。2026-11-14、macOS 27.0.1・2画面で壁衝突の`trigger=barrier`実ログと個人情報非混入、イベントタップ継続を確認。独自矩形領域の`trigger=zone`実ログは未確認。

### P1-03 修飾キー判定の基盤

- 所要：3～6時間
- 依存：P1-01、P1-02
- 作業：OS設定から修飾キー条件を読み、衝突時のグローバル修飾キー状態と照合する。
- 完了条件：条件不一致では壁だけが働き、アクションは発動しない。条件一致時だけ一回発動する。
- 安全条件：Option単独は緊急通過と競合するため、仕様を先に確定する。緊急通過を優先する案を基本とする。
- 現状：Shift・Control・Commandのビット条件を読み、現在のグローバルキー状態が条件を満たす場合だけ実行する基盤を実装。余分な既知修飾キーは許容し、未知ビットは未対応として拒否する。Optionは従来どおり緊急通過を優先し、アクション条件としては未対応と明示する。Swift 6・macOS 14最低対象の全ソースコンパイルと、条件一致・不一致・複合キー・Option予約・未知値の独立検証に合格。2026-11-14、macOS 27.0.1・2画面でShift／Control／Commandを個別に設定し、未押下時は壁のみ、押下時だけクイックメモが発火することを実衝突で確認。試験後は元のDock値へ復元。
- 合成キーの`CGEventSource`は`combinedSessionState`を維持する。Apple公式SDKヘッダはログインセッション内のイベント送信にこの状態を推奨し、`privateState`はリモート操作アプリ等の特殊用途としているため、外部レビューの`.privateState`変更案は採用しない。

## Phase 2：未実装アクション

実装は安全性と公開可能性が高い順に、一機能ずつ行う。

### P2-01 画面ロック

- 所要：2～4時間
- 候補：macOS標準ショートカットのCGEvent送信。
- 完了条件：一回だけロックし、壁の状態を安全に停止または復帰できる。解除後にカーソルがスタックしない。
- 実機試験：2画面、スリープ復帰、Option緊急通過。
- 現状：Apple公式のControl＋Command＋Qを、クイックメモ・通知センターと共通の公開CoreGraphicsキー送信処理で実装。Swift 6・macOS 14最低対象のコンパイルに合格。2026-11-14、macOS 27.0.1・2画面で実際のロック、解除後のカーソル操作、壁再開を確認。

### P2-02 クイックメモ

- 所要：3～6時間
- 候補：標準ショートカット。Fn／Globeの扱いとユーザー設定変更を調査する。
- 完了条件：既存のクイックメモを開く場合と新規作成の場合を確認し、キー配列差で誤入力しない。
- 現状：Apple公式仕様のFn／Globe＋Qを、公開CoreGraphics APIのキーイベントとして送る処理を実装。`CGPreflightPostEventAccess()`で送信権限を事前確認し、送信後は完了断定せず`requested`として扱う。Swift 6・macOS 14最低対象のコンパイルに合格。2026-11-14、macOS 27.0.1・2画面で内部コーナーからクイックメモが表示されることを確認。既存メモを開く場合と新規作成の場合の区別は未確認。

### P2-03 スクリーンセーバー開始

- 所要：3～6時間
- 候補：公開されたシステムアプリ起動経路または安定した標準ショートカット。
- 完了条件：開始、通常の入力による解除、解除後の安全な壁再開を確認する。
- 現状：公開APIの`NSWorkspace`でBundle ID `com.apple.ScreenSaver.Engine`から解決し、既知のCoreServicesパスへフォールバックして非同期起動する処理を実装。完了を断定せず`requested`として扱う。Swift 6・macOS 14最低対象のコンパイルに合格。2026-11-14、macOS 27.0.1・2画面で開始、通常入力による解除、解除後のカーソル操作と壁復帰を確認。

### P2-04 通知センター

- 所要：3～6時間
- 候補：ユーザー設定済みショートカットの利用を優先。固定の非公開通知は使用しない。
- 完了条件：開く／閉じるのトグル、再衝突キャンセル、ショートカット未設定時の説明を確認する。
- 現状：Apple公式仕様のFn／Globe＋Nを、クイックメモと共通の公開CoreGraphicsキー送信処理で実装。送信権限を事前確認し、完了を断定せず`requested`として扱う。2026-11-14、macOS 27.0.1・2画面で開閉と再衝突トグルを確認。外付けキーボード差は未検証。

### P2-05 ディスプレイをスリープ

- 所要：4～8時間
- 候補：公開APIを優先し、公開APIがなければGitHub配布で許容できるOS標準コマンドかを別途判断する。
- 完了条件：ディスプレイだけが意図どおり休止し、復帰後の5秒＋安全位置再作動が機能する。
- 注意：本体スリープとの混同、複数画面の一部だけが消える状態、外部画面の再認識を試験する。
- 現状：macOS同梱の`/usr/bin/pmset displaysleepnow`をFoundation `Process`で起動する処理を実装。実行可能性と起動例外を検出し、コマンド完了を断定せず`requested`として扱う。Swift 6・macOS 14最低対象のコンパイルとコマンド存在確認に合格。2026-11-14、macOS 27.0.1・2画面で全画面の消灯、復帰、カーソル操作、壁再開、同じ角での再発火を確認。復帰後もイベントタップ`enabled=1`を維持し、安全再作動ログを確認。

### P2-06 スクリーンセーバー無効化

- 所要：1～2日
- 依存：他の一回実行型アクションの安定後
- 難度：高
- 理由：一回実行するアクションではなく、カーソルが対象角にいる間だけ抑制する状態型機能である。
- 作業：進入、滞在、離脱、壁衝突、Option通過、画面変更、スリープ、アプリ終了の状態機械を設計する。
- 完了条件：抑制が角を離れた後やアプリ終了後に残らず、ディスプレイスリープ設定を恒久変更しない。
- 採用判断：公開された安全な抑制手段が確認できない場合は未対応のままにする。
- 現状：実装保留。公開IOKitには`kIOPMAssertionTypePreventUserIdleDisplaySleep`等があるが、Appleの説明はディスプレイのアイドルスリープ抑止であり、スクリーンセーバだけを対象角の滞在中に無効化する保証ではない。標準機能より広く画面・システムの省電力動作を妨げる可能性があるため代用しない。非公開CoreDock API、スクリーンセーバ設定の恒久変更、合成マウスイベントの定期送信も採用しない。安全な公開手段または隔離実験での同等性を確認できた場合に再開する。

## 5. 小分け作業の推奨順

当面は公開準備より未実装機能を優先し、次の順で一項目ずつ進める。

0. P0-02のうちローカルGit履歴だけを開始する。これは公開作業ではなく、機能開発中に安定版へ戻れるようにする安全措置とする。GitHubリポジトリ作成や外部へのpushは行わない。
1. P1-01：OS別アクション表を作り、現在のmacOSで設定値と実行候補を確認する。
2. P1-02：ActionExecutorを整理し、追加アクションが壁制御へ影響しない基盤を作る。
3. P2-02：クイックメモ。画面状態を大きく変えず、失敗時も戻しやすいため最初の追加機能とする。
4. P2-04：通知センター。開閉をすぐ確認でき、スリープやロックを伴わないため次に実装する。
5. P2-03：スクリーンセーバー開始。開始・解除後の壁再開を含めて確認する。
6. P2-01：画面ロック。実装自体は比較的単純だが、試験のたびにロック解除が必要なためスクリーンセーバーの後に行う。
7. P2-05：ディスプレイスリープ。画面再認識とスリープ安全機構への影響があるため後段で扱う。
8. P2-06：スクリーンセーバー無効化。一回実行型ではなく、進入から離脱まで状態を保持する最難関として最後に実装する。
9. P1-03：修飾キー基盤。追加機能がそろった後で全機能へ共通適用する。Option緊急通過との競合仕様を先に確定する。
10. Phase 3：日英UI、自動テスト、実機回帰をまとめて仕上げる。
11. Phase 4・5：GitHub公開を決定した段階まで保留する。

この順序は「容易な順」だけではなく、「失敗時に通常操作へ戻りやすい順」である。ロック、ディスプレイスリープ、スクリーンセーバー無効化は、実装途中の誤作動が操作継続へ影響し得るため、クイックメモと通知センターで追加アクション基盤を安定させてから着手する。

短い作業枠では、調査と実装を同時に広げない。例えばP2-04を開始した場合、通知センターの手段、テスト、文書更新まで完了または明確に保留してから次へ進む。

2026-11-14、追加アクション、修飾キー、プライバシー配慮済み統合ログを実機確認したbeta 2 (48)のアプリZIPを内容変更せず、v0.11.0 RC1候補として固定。未検証事項はREADMEに残し、RC1を正式安定版とは扱わない。

## 6. バージョン案

- v0.10.x：現行機能の不具合修正のみ
- v0.11.0：修飾キー基盤と、安全に実装できた追加アクション
- v0.12.0：状態型アクションを採用できた場合
- v0.90.0：GitHub公開候補ベータ
- v1.0.0：公開チェックリストと複数環境試験を完了した安定版

機能数をそろえるためだけに版を上げない。公開APIで安全に再現できない標準機能が残っていても、未対応理由を明示できれば公開候補に進める。

## 7. 見積もり

- 未実装機能の個人用試作：2～4作業日
- 公開可能なソース版：追加で3～6作業日
- Developer ID署名済みバイナリ：追加で2～4作業日
